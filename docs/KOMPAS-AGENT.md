# KOMPAS-AGENT: операционная инструкция для агентов

> **Назначение.** Этот файл — исполняемая инструкция для ИИ-агентов, которые
> ведут итеративное улучшение ИИ-системы по методике КОМПАС (Герберт Саймон +
> тройная петля обучения). Обоснование и теория: `docs/simon-iterative-ai-learning.md`.
> Агенту достаточно этого файла; теорию читать только при споре о правилах.
>
> **Версия протокола:** 1.0

---

## 0. Как пользоваться (читать первым)

1. Определи свою **роль** (раздел 2). Выполняй только действия своей роли.
2. Прочитай **состояние** в каталоге `kompas/` (раздел 3). Если его нет — выполни `INIT` (раздел 4).
3. Определи текущую **петлю** по `kompas/state.yaml → loop`.
4. Выполни процедуру петли (разделы 5–7) **строго по шагам**.
5. Запиши результат в форматах из раздела 9. Не оставляй выводы только в чате.
6. Перед завершением проверь **инварианты** (раздел 8) и **сигналы эскалации** (разделы 5.3, 6.3).
7. Передай работу через `kompas/handoff.md` (раздел 10).

Язык записей: русский. Ключи YAML/JSON — латиницей, как в шаблонах.

## 1. Словарь

| Термин | Значение для агента |
|---|---|
| **Система** | Улучшаемая ИИ-система: модель + промпты + инструменты + данные + пайплайн |
| **Чекпоинт** | Зафиксированная, прошедшая проверки версия системы (устойчивая подсборка) |
| **Пространство задачи** | Файл `kompas/problem_space.yaml`: представление задачи, модули, тест цели, операторы |
| **Рамка** | Файл `kompas/frame.yaml`: ценностные и фактические посылки, внешняя среда |
| **Различие** | Кластер ошибок, отделяющий текущее поведение от целевого |
| **Оператор** | Тип вмешательства, уменьшающий различие (см. 5.2, шаг 4) |
| **A** | Уровень притязаний: порог, при котором результат итерации «достаточно хорош» |
| **B** | Бюджет итерации: вычисления, время, часы эксперта |
| **Тупик** | Ситуация, в которой поиск в текущей петле больше не даёт прогресса (сигналы Т2/Т3) |
| **Чанк / навык** | Повторно используемый фрагмент решения в `kompas/library/` |

## 2. Роли

| Роль | ID | Петли | Может менять | Не может менять |
|---|---|---|---|---|
| Оператор цикла | `operator` | 1 | данные, примеры, промпты, конфиги обучения, `library/`, `iterations/` | `problem_space.yaml`, `frame.yaml` |
| Аналитик ошибок | `analyst` | 1, 2 | `clusters/`, отчёты | систему, `frame.yaml` |
| Архитектор представления | `architect` | 2 | `problem_space.yaml`, `diff_table.yaml` | `frame.yaml` |
| Фасилитатор рамки | `framer` | 3 | черновик `frame.proposal.yaml` | `frame.yaml` (утверждает только человек) |
| Человек-эксперт / владелец | `human` | 1–3 | всё | — |

**Правило:** если для действия нужна чужая роль — не выполняй его, а запиши запрос в `handoff.md`.

## 3. Состояние (единственный источник правды)

```
kompas/
  state.yaml             # текущая петля, A, B, счётчики, активный чекпоинт
  frame.yaml             # петля 3: ценностные/фактические посылки
  problem_space.yaml     # петля 2: представление, модули, тест цели
  diff_table.yaml        # таблица различий: кластер → операторы
  clusters/              # отчёты кластеризации ошибок по итерациям
  iterations/NNNN.yaml   # журнал каждой итерации петли 1
  sessions/              # протоколы петель 2 и 3
  library/               # чанки: правила, примеры, навыки
  handoff.md             # передача работы следующему агенту
```

### 3.1. `state.yaml`

```yaml
protocol_version: "1.0"
loop: 1                    # 1 | 2 | 3
epoch: 1                   # номер эпохи (меняется после петли 3)
representation_version: 1  # меняется после петли 2
iteration: 0               # последний номер итерации петли 1
checkpoint: null           # id активного чекпоинта
aspiration_A: null         # число в шкале основной метрики
budget_B:
  compute: null
  wall_time_hours: null
  expert_minutes: 30
counters:
  easy_successes_in_row: 0
  failures_in_row: 0
  iterations_without_gain: 0
  representation_changes_without_exit: 0
history:
  best_metric: null
  metric_series: []        # [{iteration, metric}]
```

### 3.2. `frame.yaml`

```yaml
goal_of_epoch: ""
value_premises: []         # что считаем хорошим/вредным/приоритетным
fact_premises: []          # что считаем правдой о пользователях, данных, среде
outer_environment:
  users: []
  conditions: []
  risks: []
forbidden_capabilities: [] # что система НЕ должна уметь
success_criteria: []
approved_by: ""            # заполняет только human
approved_at: ""
```

### 3.3. `problem_space.yaml`

```yaml
task: ""
representation:
  input_format: ""
  output_format: ""
  modules:
    - id: ""
      responsibility: ""
      test: ""             # команда или набор оценки модуля
      interface: ""        # что получает и что отдаёт
goal_test:
  primary_metric: ""
  secondary_metrics: []
  eval_command: ""
  regression_suites: []

```

### 3.4. `diff_table.yaml`

```yaml
- difference: ""           # имя кластера/типа ошибки
  signature: ""            # признак, по которому распознаём
  operators:               # в порядке предпочтения
    - type: transfer       # transfer | environment | examples | finetune
      action: ""
      tried: 0
      succeeded: 0
```

## 4. Процедура INIT

Выполняется, если `kompas/` отсутствует.

1. Создай структуру из раздела 3.
2. Заполни `problem_space.yaml` по фактическому устройству системы. Неизвестные поля оставь пустыми и перечисли в `handoff.md → открытые вопросы`.
3. Создай черновик `frame.proposal.yaml`; `frame.yaml` не заполняй — его утверждает `human`.
4. Прогони `goal_test.eval_command`. Запиши метрику как `history.best_metric`.
5. Установи `aspiration_A = best_metric + минимальный значимый прирост` (если неизвестен — 2% относительно).
6. Установи `loop: 1`, `iteration: 0`.
7. Запиши `handoff.md`.

## 5. Петля 1 — поиск в пространстве задачи

**Цель:** уменьшить главное различие в рамках текущего представления.
**Роли:** `operator`, `analyst`.

### 5.1. Предусловия

- `frame.yaml` утверждён (`approved_by` не пуст). Иначе: только измерение и кластеризация, без изменений системы.
- `problem_space.yaml` существует и содержит `goal_test.eval_command`.

### 5.2. Шаги

1. **Измерь.** Выполни `eval_command` и `regression_suites`. Сохрани ошибки вместе с трассами (вход, выход, промежуточные шаги, рассуждение).
2. **Кластеризуй** (`analyst`). Сгруппируй провалы по общим признакам. Для каждого кластера: размер, 3–5 репрезентативных примера, гипотеза причины, сигнатура. Ищи инварианты: что общего у всех провалов кластера и чего нет у успехов. Сохрани в `clusters/NNNN.yaml`.
3. **Выбери главное различие.** Приоритет = `размер × важность / ожидаемая_стоимость_исправления`. Возьми один кластер.
4. **Выбери оператор** из `diff_table.yaml` в строгом порядке предпочтения:
   1. `transfer` — передать знание без обучения: правило, инструмент, инструкция, валидатор;
   2. `environment` — исправить среду: данные, разметку, задания, награду, формат;
   3. `examples` — добавить разобранные примеры;
   4. `finetune` — дообучить модуль.

   Переход к следующему типу допустим только с письменным обоснованием, почему предыдущий не подходит.
5. **Одно изменение — одна гипотеза.** Сформулируй: «Если сделать X, кластер K уменьшится на Y, без регрессий в модулях M». Внеси ровно одно изменение.
6. **Проверь.** Повтори шаг 1 полностью, включая регрессии всех модулей.
7. **Реши:**
   - `accept`, если основная метрика ≥ `A` **или** кластер уменьшился на ожидаемую величину, **и** нет регрессий выше допуска → создай новый чекпоинт.
   - иначе `rollback` → верни предыдущий чекпоинт.
8. **Сожми опыт.** При `accept` вынеси в `library/` то, что можно переиспользовать: правило, пример, навык. При `rollback` запиши в `diff_table.yaml`, что оператор не сработал (`tried += 1`).
9. **Обнови притязания и счётчики:**
   - лёгкий успех (принят с первой попытки, использовано < 50% B): `easy_successes_in_row += 1`; при значении 2 → `A ← A + δ`, счётчик сбрось;
   - неудача: `failures_in_row += 1`;
   - прирост метрики < ε: `iterations_without_gain += 1`, иначе сбрось.
   - **Не снижай `A` самостоятельно.** Снижение — только решение `architect` или `human` в петле 2.
10. **Запиши журнал** `iterations/NNNN.yaml` (раздел 9.1) и обнови `state.yaml`.
11. **Проверь сигналы Т2** (5.3). Если сработал хотя бы один — установи `loop: 2` и передай `architect`.

### 5.3. Сигналы Т2 (эскалация в петлю 2)

Значения по умолчанию: `N = 3`, `ε = 0.5%` относительно, `ρ = 20%`.

| ID | Условие (проверяемое) |
|---|---|
| Т2.1 Плато | `iterations_without_gain ≥ N` и для главного кластера все операторы в `diff_table` имеют `tried ≥ 1` |
| Т2.2 Осцилляция | Два последних принятых изменения вызвали регрессию в модулях, которые чинили предыдущие изменения |
| Т2.3 Расхождение | Метрика выросла, но `human`/эксперт отметил ухудшение в ≥ 2 итерациях из последних 5 |
| Т2.4 Неклассифицируемые | Доля провалов вне известных кластеров > ρ |
| Т2.5 Дорожание | Стоимость единицы прироста выросла ≥ 2× за последние N итераций |
| Т2.6 Провалы подряд | `failures_in_row ≥ N` |

## 6. Петля 2 — смена представления

**Цель:** изменить постановку задачи так, чтобы поиск в петле 1 снова давал прогресс.
**Роли:** `architect` (ведёт), `analyst`, `human` (утверждает).

### 6.1. Предусловие

Зафиксирован хотя бы один сигнал Т2 с доказательствами (номера итераций, графики, примеры).

### 6.2. Шаги

1. **Факты тупика.** Перечисли сработавшие сигналы и доказательства.
2. **Протокольный разбор.** Возьми 20–50 трасс из проблемных кластеров. Опиши, *как система фактически понимает задачу*: какие подцели ставит, какие шаги делает, где теряется.
3. **Изоморфы.** Предложи **не менее трёх** альтернативных представлений. Направления:
   - другой формат входа/выхода;
   - другая гранулярность шагов (крупнее/мельче);
   - перенос части работы в инструмент или детерминированный код;
   - другой порядок подцелей;
   - другое разбиение на модули.

   Для каждого: ожидаемый эффект, стоимость, риски, как опровергнуть.
4. **Декомпозиция.** Перерисуй модули так, чтобы связи внутри модуля были сильными, а между модулями — слабыми и явно описанными в `interface`. Признак плохой декомпозиции — Т2.2.
5. **Тест цели.** Сравни метрики с суждениями эксперта на 20+ примерах. Где расходятся — предложи замену или дополнение метрики.
6. **Опровергающие примеры.** Для каждого кандидата подбери примеры, на которых он должен провалиться, если гипотеза неверна. Проверь.
7. **Пилот.** Для 1–2 лучших кандидатов выполни 1–2 итерации петли 1 в новом представлении (в отдельной ветке/копии). Сравни прирост на единицу бюджета со старым представлением.
8. **Решение** (`human` утверждает):
   - обнови `problem_space.yaml`, `diff_table.yaml`, `representation_version += 1`;
   - задай новый `A` для новой постановки;
   - сбрось счётчики петли 1;
   - `representation_changes_without_exit += 1`, если пилот не вывел с плато, иначе сбрось в 0.
9. Запиши протокол `sessions/L2-NNN.md` (раздел 9.2). Установи `loop: 1` или, при сигнале Т3, `loop: 3`.

### 6.3. Сигналы Т3 (эскалация в петлю 3)

| ID | Условие |
|---|---|
| Т3.1 | `representation_changes_without_exit ≥ 2` |
| Т3.2 | Цели `success_criteria` достигнуты, но `human` фиксирует недовольство пользователей/заказчика |
| Т3.3 | Два требования из `value_premises` противоречат друг другу на конкретных примерах |
| Т3.4 | Изменилась внешняя среда: новые пользователи, риски, инструменты, правила |
| Т3.5 | Плановая точка: конец эпохи |

## 7. Петля 3 — смена рамки

**Цель:** пересмотреть, *зачем* и *для кого* решается задача.
**Роли:** `framer` готовит материалы; **решение принимает только `human`.**

### 7.1. Шаги для `framer`

1. **Инвентаризация посылок.** Выпиши из `frame.yaml` и фактического поведения системы:
   - ценностные посылки (явные и неявные — принятые без обсуждения);
   - фактические посылки и доказательства для каждой; отметь непроверенные.
2. **Множественные рамки.** Опиши задачу минимум с трёх позиций (например: пользователь, оператор системы, затронутая третья сторона). Для каждой: цель, метрика, граница системы и среды, что считается вредом.
3. **Вопрос «нужно ли учиться».** Для каждой крупной способности: можно ли передать знание правилом, инструментом, процессом или людьми вместо обучения?
4. **Опционность.** Для каждого варианта рамки: какие будущие направления он открывает и какие закрывает.
5. **Предложение.** Запиши `frame.proposal.yaml` и `sessions/L3-NNN.md` с вопросами из 7.2.
6. **Остановись.** Установи в `handoff.md` статус `WAITING_HUMAN`. Не продолжай петлю 1 до утверждения.

### 7.2. Обязательные вопросы для человека

- Какие ценностные посылки мы приняли без обсуждения?
- Что изменилось во внешней среде с прошлой эпохи?
- Как выглядит цель с позиции каждого участника?
- Что система **не должна** уметь?
- Где обучение — не лучший способ передать знание?
- Какие направления закрывает текущая рамка, и стоит ли их держать открытыми?

### 7.3. После утверждения

`frame.yaml` ← утверждённое предложение, `epoch += 1`, `loop: 2` (новая рамка почти всегда требует пересмотра представления).

## 8. Инварианты (проверять перед каждым завершением работы)

1. **Одно изменение на итерацию.** Нельзя смешивать несколько гипотез.
2. **Нет принятия без регрессий.** Каждое `accept` сопровождается прогоном всех `regression_suites`.
3. **Откат всегда возможен.** Предыдущий чекпоинт сохранён и указан в журнале.
4. **Ценности не меняются снизу.** Ни одна роль, кроме `human`, не меняет `frame.yaml`.
5. **Представление не меняется в петле 1.** `problem_space.yaml` меняет только `architect` в петле 2.
6. **A не снижается молча.** Снижение порога — только с записью причины в протоколе петли 2.
7. **Бюджет соблюдается.** При исчерпании `B` — остановись, запиши частичный результат, передай работу.
8. **Внимание эксперта экономится.** Человеку отправляется не более 5 кластеров за итерацию, каждый с 3–5 примерами и гипотезой причины. Сырые логи не отправлять.
9. **Всё записано.** Решения, гипотезы и результаты лежат в `kompas/`, а не только в чате.
10. **Честность.** Не выдавать непроверенное за проверенное: если тест не запускался — так и написать.

## 9. Форматы записей

### 9.1. Журнал итерации `iterations/NNNN.yaml`

```yaml
iteration: 12
agent_role: operator
checkpoint_before: ckpt-011
aspiration_A: 0.78
budget_B_used: {compute: "", wall_time_hours: 1.5, expert_minutes: 10}
main_difference:
  cluster: "неверные единицы измерения"
  size: 41
  hypothesis_of_cause: ""
operator:
  type: transfer          # transfer | environment | examples | finetune
  action: ""
  why_not_cheaper: ""     # обязательно, если type != transfer
prediction: "кластер уменьшится до ≤ 10, без регрессий в модулях parse, format"
result:
  metric_before: 0.74
  metric_after: 0.77
  cluster_size_after: 8
  regressions: []         # [{module, before, after}]
decision: accept          # accept | rollback
checkpoint_after: ckpt-012
compressed_to_library: ["library/rules/units.md"]
counters_after: {easy_successes_in_row: 1, failures_in_row: 0, iterations_without_gain: 0}
signals_T2: []            # например ["T2.1"]
notes: ""
```

### 9.2. Протокол петли 2 `sessions/L2-NNN.md`

```markdown
# L2-NNN — смена представления
- Сигналы: T2.x (доказательства: итерации …)
- Как система понимает задачу сейчас: …
- Кандидаты-изоморфы:
  1. … (эффект / стоимость / риск / как опровергнуть)
  2. …
  3. …
- Новая декомпозиция: …
- Расхождения метрики и эксперта: …
- Результаты пилота: …
- Решение и кто утвердил: …
- Новый A: … (причина)
```

### 9.3. Протокол петли 3 `sessions/L3-NNN.md`

```markdown
# L3-NNN — смена рамки
- Сигналы: T3.x
- Ценностные посылки (явные / неявные): …
- Фактические посылки (проверенные / непроверенные): …
- Рамки (≥ 3 позиции): …
- Где обучение не нужно: …
- Опционность вариантов: …
- Вопросы для human: …
- Статус: WAITING_HUMAN
```

## 10. Передача работы `handoff.md`

Перезаписывается в конце каждой сессии агента.

```markdown
# Handoff
- Статус: IN_PROGRESS | WAITING_HUMAN | BLOCKED | DONE
- Петля / эпоха / версия представления: 1 / 2 / 3
- Последняя итерация: NNNN, решение: accept|rollback
- Активный чекпоинт: …
- Что сделано в этой сессии: …
- Следующий шаг (одно действие): …
- Следующая роль: operator | analyst | architect | framer | human
- Открытые вопросы к human: …
- Сработавшие сигналы: …
```

## 11. Шаблоны запуска агентов

Вставляйте в системный промпт или первое сообщение субагента.

### 11.1. Оператор цикла

```
Ты — analyst по протоколу docs/KOMPAS-AGENT.md. Не меняй систему.

размер, 3–5 примеров, гипотеза причины, сигнатура. Человеку — не более
5 кластеров.
```
